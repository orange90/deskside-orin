# YOLO26s-Pose / m-Pose：现有照片与 Orin 性能对比

2026-11-11，用户要求用已有照片评估两个候选，不替换现有模型；随后要求对历史未知照片给出编号图片供人工复核，并讨论 Qwen-VL。实验全程使用独立目录和环境，生产模型、代码及选择配置哈希核对未变。

结论：两个候选在当前照片中都能提供比原姿态模块更完整的上半身骨骼，但未解决完全椅背遮挡；套用当前关节几何规则仍不能得出可靠坐站标签。m 未表现出足以支持升级的明确收益。若继续试验 Pose，优先成本较低的 s；另可独立测试视觉大模型对整体姿态的判断，暂不切换线上模型。

## 实测延迟

AGX Orin 64GB、MODE_30W、CUDA 12.6、TensorRT 10.3。640×640、batch=1，生产视觉/Qwen/Cosmos 继续运行。每模型预热 12 次，4 张图片各全图和工位裁剪两种输入、25 轮，共 200 次同步墙钟计时。

| 方案 | 中位耗时 | P95 | 权重/引擎大小 |
|---|---:|---:|---|
| 原 RTMDet-tiny + RTMPose-s，TensorRT | 53.8 ms | 72.7 ms | 原有引擎 |
| YOLO26s-Pose，PyTorch FP16 | 63.9 ms | 87.5 ms | PT 23.0 MiB |
| YOLO26m-Pose，PyTorch FP16 | 65.2 ms | 125.2 ms | PT 46.8 MiB |
| YOLO26s-Pose，TensorRT FP16 | 56.3 ms | 76.5 ms | 引擎 29.7 MiB |
| YOLO26m-Pose，TensorRT FP16 | 98.5 ms | 124.6 ms | 引擎 53.6 MiB |

计时包含预处理、推理、后处理、结果转 CPU 与几何姿态规则，不含磁盘读取、摄像头、Cosmos、状态稳定及看板刷新。TensorRT 两个引擎均使用 builder optimization level 0、2 GiB workspace；默认优化构建等待约 15 分钟后取消，最终使用一致的快速构建档，以上不是充分调优速度。m 的快速引擎没有优于其 PyTorch 中位耗时，不应假定 TensorRT 必然更快。

两者组件 P95 都在 5 FPS 对应的每帧 200ms 预算内，不能据此宣称整套视觉、语音并发或有效坐站切换 P95≤3 秒通过。测试期间原生产帧计数窗口平均约 6.2 FPS；瞬时显示最低曾有 4.5 FPS。最终三项服务均就绪，实验 Python 进程已退出。

实验进程峰值 RSS：s TensorRT 930.6 MiB、m TensorRT 927.4 MiB，包含 Python/PyTorch 框架，不能当作纯模型或全部 GPU 内存。模型可放入本机；测试构建期间仍有约 38.8 GiB 可用内存。

## 四张主样本

检测阈值 0.28，高置信关节阈值 0.55。以下为完整画面结果：

| 样本 | 原检测/姿态模块 | YOLO26s-Pose TRT | YOLO26m-Pose TRT |
|---|---|---|---|
| 明显站立、腿部被挡 | 检出人，1 个高置信关节 | 检出人，8 个 | 检出人，8 个 |
| 明显坐姿 | 未检出人 | 检出人，4 个 | 检出人，6 个 |
| 用户确认仍坐着、被椅背完全挡住 | 未检出人 | 未检出人 | 未检出人 |
| 用户确认离开时的空工位 | 未检出人 | 未检出人 | 未检出人 |

在相同工位 ROI 下，原模型能检出明显坐姿，但仅 1 个高置信关节；s/m 分别为 5/6 个。站姿 s/m 为 7/8 个。两个候选在全图和 ROI 都未补出完全遮挡的人。

“高置信关节更多”并不等于更准确：分数未在不同模型之间校准，m 额外点包含不可直接验证的遮挡部位。本次没有逐关节点人工真值，不报告关键点 mAP 或泛化准确率。固定图片也无法验收连续时长误差和切换延迟。

YOLO 只输出框和骨骼。把输出送入与现有 RTMPose 同尺度的 `leg_posture` 后，明显坐/站图依然 unknown：缺少可靠髋膝踝组合。实验 JSON 中 away 是原始“未检出人”的映射，不是生产离开结论；生产还有 Cosmos/遮挡/连续状态逻辑。

## Qwen 视觉路线：讨论，尚未部署

用户提出通用视觉大模型可能更适合整体姿态判断。当前 Cosmos 已承担类似复核，但旧照片上也有判错，不能把换 VLM 当作已解决。

候选为已有 Qwen3.5-4B 补齐匹配视觉编码器，或独立 Qwen3-VL-4B-Instruct。当前 Orin 的 Qwen 进程只加载文本 GGUF，没有 mmproj，本轮未下载或加载新的 Qwen 视觉权重。官方支持图片输入不等于当前进程已具备图像能力，图像编码、推理延迟与并发资源需另测。

建议 VLM 对场景做语义判断，时间连续性负责计时，Pose 提供辅助运动与骨骼；先用同一批未知/误判图片盲评，不提供旧标签，给用户看图确认，再决定是否改变架构。
